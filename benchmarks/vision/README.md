# Qwen3.6 vision performance on GB10

This benchmark compares native SparkLab's experimental Triton vision path with
vLLM 0.28.0 on the same pinned NVIDIA Qwen3.6-35B-A3B-NVFP4 checkpoint:
`491c2f1ea524c639598bf8fa787a93fed5a6fbce`.

It uses synthetic colored-shape PNGs generated by `bench_openai.py`: one 256×256
image, one 1024×1024 image, and two 512×512 images. The prompt asks for detailed
shape descriptions and reconstruction instructions. Each case has one warmup
and three measured requests at concurrency one, temperature zero, thinking off,
and exactly 128 output tokens (`ignore_eos=true`). This is a fixed-work
performance probe, not a vision accuracy benchmark or a natural stopping test.

The prompt sizes are 121, 1,081 and 571 tokens, respectively. Both engines must
report identical input and output counts. Decode tok/s uses server completion
usage divided by the interval from the first through last nonempty content
chunk, excluding one token. This is a client streaming approximation, especially
when speculative decoding emits several tokens per chunk. End-to-end latency
includes preprocessing, vision encoding, prefill, generation and final usage.
TTFT measures request start to the first nonempty content chunk; it is not an
isolated prefill or vision-encoder measurement.

## Profiles

- **SparkLab native:** committed native vision support, host Torch 2.11, Triton
  text kernels, all 10,240 routed experts preloaded, BF16 vision and KV cache,
  eager and target-only execution.
- **vLLM target baseline:** v0.28.0, Marlin experts, FlashInfer attention, BF16 KV,
  eager and target-only execution. Numerical kernels differ from SparkLab.
- **vLLM recipe-derived:** the linked [GB10 NVFP4 recipe](https://recipes.vllm.ai/Qwen/Qwen3.6-35B-A3B?variant=nvfp4)
  supplies Marlin, FlashInfer, FP8 KV and Triton MTP3. For this bounded comparison
  we use 8,192 context tokens, one active request, a maximum graph capture size
  of eight, and disable prefix/multimodal processor caches. These are deliberate
  deviations from the recipe's full-context serving profile.

All servers run sequentially on one GB10. The source image processor is limited
to 65,536–1,048,576 pixels on both backends. SparkLab image prompts bypass prefix
reuse; vLLM prefix caching and multimodal processor caching are disabled.
The machine has pre-existing swap; this is not a zero-swap certification run.
The recipe's published text-only SPEED-Bench numbers are not vision results.

## Reproduce

Install the source environment's `vision` extra. Keep both the original source
snapshot and SparkLab's matching Triton FTW (recipe 0.5.0).

```bash
SPARKLAB_DISABLE_KERNEL_CACHE=1 sparklab serve \
  --model /path/to/qwen36/triton-ftw \
  --vision-model /path/to/qwen36/source \
  --served-model-name qwen36-vision-bench \
  --host 127.0.0.1 --port 18361 \
  --moe-backend offload --moe-storage disk --moe-host-cache-gb 0 \
  --moe-cache-size 10240 --moe-preload-all \
  --nvfp4-backend triton --attention-backend triton \
  --num-tokens 8192 --max-seq-len-override 8192 \
  --max-running-requests 1 --speculative-tokens 0
```

After `/health` reports `status: ok`, run:

```bash
python benchmarks/vision/bench_openai.py \
  --url http://127.0.0.1:18361 --profile sparklab-triton-target \
  --output results/vision/sparklab.json
```

Stop SparkLab before launching vLLM. Run each profile separately, waiting for
HTTP 200 from its `/health` before benchmarking:

```bash
benchmarks/vision/serve_vllm.sh /path/to/qwen36/source target
python benchmarks/vision/bench_openai.py \
  --url http://127.0.0.1:18362 --profile vllm-marlin-eager-target-bf16 \
  --output results/vision/vllm-target.json
docker stop sparklab-vision-bench-vllm-target

benchmarks/vision/serve_vllm.sh /path/to/qwen36/source recipe
python benchmarks/vision/bench_openai.py \
  --url http://127.0.0.1:18362 --profile vllm-marlin-mtp3-fp8-graphs \
  --output results/vision/vllm-recipe.json
docker stop sparklab-vision-bench-vllm-recipe
```

The launcher retains stopped containers for their logs. Remove those benchmark
containers before rerunning with the same names. Cold startup and per-case
warmup measurements are excluded from the medians, but warmups are retained in
the JSON. Image bytes are identified by SHA256, and generated outputs are saved.

## Measured results — 2026-09-10

Three-trial medians on one GB10; all values below are measured vision requests.

| Workload | Profile | TTFT (s) | Decode (tok/s) | End-to-end (s) |
|---|---|---:|---:|---:|
| image_256 | SparkLab Triton target | 0.238 | 43.03 | 3.188 |
| image_256 | vLLM eager target | 0.120 | 27.68 | 4.709 |
| image_256 | vLLM MTP3 + graphs | 0.123 | 100.99 | 1.381 |
| image_1024 | SparkLab Triton target | 0.871 | 42.68 | 3.847 |
| image_1024 | vLLM eager target | 0.378 | 27.80 | 4.945 |
| image_1024 | vLLM MTP3 + graphs | 0.357 | 109.79 | 1.514 |
| two_images_512 | SparkLab Triton target | 0.510 | 42.35 | 3.509 |
| two_images_512 | vLLM eager target | 0.223 | 25.36 | 5.230 |
| two_images_512 | vLLM MTP3 + graphs | 0.215 | 115.44 | 1.315 |

The tuned vLLM profile has 2.35–2.73× the measured decode throughput of the
current native SparkLab vision profile. Its end-to-end latency is 57–63% lower.
SparkLab beats the eager target-only vLLM baseline in decode throughput, but
vLLM has lower first-token latency in both configurations. These differences
combine kernels, execution mode and (for the tuned profile) speculation and KV
precision; they do not isolate one optimization or establish output-quality parity.

All 36 requests succeeded, including nine warmups, with matching image hashes
and prompt lengths across profiles and exactly 128 output tokens each.
[Full trial records and outputs](../gb10/results/GB10-QWENVISIONPERF-001.json).
The original port-1919 service was stopped for the runs and restored afterward.
